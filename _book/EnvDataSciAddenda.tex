For a start, you'll need to have R and \index{RStudio}RStudio installed, then you'll need to install various \index{packages}packages to support specific chapters and sections. No instructions are provided here, since you should know how to install packages in RStudio.

From time to time, you'll want to update your installed packages, and that usually happens when something doesn't work and maybe the dependencies of one package on another gets broken with a change in a package. Fortunately, in the R world, especially at the main repository at CRAN, there's a lot of effort put into making sure packages work together, so usually there are no surprises if you're using the most current versions.

Once a package like \texttt{dplyr} is installed, you can access all of its functions and data by adding a library call, like \ldots{}

\begin{Shaded}
\begin{Highlighting}[]
\FunctionTok{library}\NormalTok{(dplyr)}
\end{Highlighting}
\end{Shaded}

\ldots{} which you \emph{will} want to include in your code, or to provide access to multiple libraries in the tidyverse, you can use \texttt{library(tidyverse)}. Alternatively, if you're only using maybe one function out of an installed package, you can call that function with the \texttt{::} separator, like \texttt{dplyr::select()}. This method has another advantage in avoiding problems with duplicate names -- and for instance we'll generally call \texttt{dplyr::select()} this way.

Raw data such as \texttt{.csv} files can also be read from the \texttt{extdata} folder that is installed on your computer when you install the package, using code such as:

\begin{verbatim}
csvPath <- system.file("extdata","TRI/TRI_1987_BaySites.csv", package="igisci")
TRI87 <- read_csv(csvPath)
\end{verbatim}

or something similar for shapefiles, such as:

\begin{verbatim}
shpPath <- system.file("extdata","marbles/trails.shp", package="igisci")
trails <- st_read(shpPath)
\end{verbatim}

And we'll find that including most of the above arcanity in a function will help. We'll look at functions later, but here's a function that we'll use a lot for setting up reading data from the extdata folder:

\begin{verbatim}
ex <- function(dta){system.file("extdata",dta,package="igisci")}
\end{verbatim}

And this \texttt{ex()}function is needed so often that it's installed in the \texttt{igisci} package, so if you have \texttt{library(igisci)} in effect, you can just use it like this:

\begin{verbatim}
trails <- st_read(ex("marbles/trails.shp"))
\end{verbatim}

But how do we see what's in the \texttt{extdata} folder? We can't use the \texttt{data()} function, so we would have to dig for the folder where the igisci package gets installed, which is buried pretty deeply in your user profile. So I wrote another function \texttt{exfiles()} that creates a data frame showing all of the files and the paths to use. In RStudio you could access it with \texttt{View(exfiles())} or we could use a datatable (you'll need to have installed ``DT''). You can use the path using the \texttt{ex()} function with any function that needs it to read data, like \texttt{read.csv(ex(\textquotesingle{}CA/CA\_ClimateNormals.csv\textquotesingle{}))}, or just enter that \texttt{ex()} call in the console like \texttt{ex(\textquotesingle{}CA/CA\_ClimateNormals.csv\textquotesingle{})} to display where on your computer the installed data reside.

\hypertarget{air-pollutant-emissions-trends-epa}{%
\chapter{Air pollutant emissions trends (EPA)}\label{air-pollutant-emissions-trends-epa}}

The National Emissions Inventory (NEI) program of the US EPA is a detailed estimate of air emissions of criteria and hazardous air pollutants from a wide variety of air emissions sources. The inventory is released every three years based primarily upon data provided by state, local, and tribal air resources agencies for pollution sources they monitor, supplemented by data developed by the US EPA.

Air pollutant data were downloaded from \url{https://www.epa.gov/air-emissions-inventories/air-pollutant-emissions-trends-data} and provided in the igisci package.

Processing these data to create a \texttt{free\_y} faceted graph (\ref{fig:USairpollution}) employs several data transformation methods we've looked at, and some we haven't:

\begin{itemize}
\tightlist
\item
  \texttt{summarize\_all} gets means of all variables, though since we're just using the totals, this just causes worksheets with multiple \texttt{Total} rows to merge into one; they're actually the same value
\item
  \texttt{pivot\_longer} is used twice, first to create columns for each pollutant, so the columns can be binded together, then later to create a facet graph where each pollutant becomes a parameter factor
\item
  \texttt{bind\_cols} to combine a series of data frames with each having the same years (1990:2016) when data for all parameters were collected
\item
  A fix for dealing data not all being read in as numeric, needed for an entry error for the NH3 data, was developed by first reading in the \texttt{Source\ Category} column, then the yearly data values, setting \texttt{col\_types="numeric"}, then binding the columns
\end{itemize}

\hypertarget{goals-and-basic-methods-of-the-analysis}{%
\section{Goals and basic methods of the analysis}\label{goals-and-basic-methods-of-the-analysis}}

Our general goal, inspired by Studwell et al. (\protect\hyperlink{ref-Studwell2017}{2017}), is to look at what variables influence the counts of specific seabirds and develop predictive models and maps illustrating optimal conditions for those seabirds based on the model. We're expecting that some of the various measurements and conditions could be good predictors, though recognizing that no model is perfect and there are going to be many other factors we can't account for.

Our basic method will include:

\begin{itemize}
\tightlist
\item
  Gathering data collected on the cruises as well as GIS and model-derived measurements (e.g.~depth, distance, climate models). \emph{This has been done and all variables we'll use are included in the transects shapefile.}
\item
  Explore the data using maps, graphs and tables, filtering for a time frame and complete data.
\item
  Select a species, timeframe, and selection of explanatory variables.
\item
  Use \texttt{glm} to model the species counts responding to the explanatory variables, using the poisson family.
\item
  Map the results.
\end{itemize}

The flux tower data were collected at a high frequency for eddy covariance processing where 3D wind speed data are used to model the movement of atmospheric gases, including CO\textsubscript{2} flux driven by photosynthesis and respiration processes. Note that the sign convention of CO\textsubscript{2} flux is that positive flux is release to the atmosphere, which might happen when less photosynthesis is happening but respiration and other CO\textsubscript{2} releases continue, while a negative flux might happen when more photosynthesis is capturing more CO\textsubscript{2}.

A spreadsheet of 30-minute summaries from 17 May to 6 September can be found in the \texttt{igisci} extdata folder as \texttt{"meadows/LoneyMeadow\_30minCO2fluxes\_Geog604.xls"}, and includes data on photosynthetically active radiation (PAR), net radiation (Qnet), air temperature, relative humidity, soil temperature at 2 and 10 cm depth, wind direction, wind speed, rainfall, and soil volumetric water content (VWC). There's clearly a lot more we can do with these data (see Blackburn, Oliphant, and Davis (\protect\hyperlink{ref-blackburn2021carbon}{2021})), but we'll look at CO\textsubscript{2} flux and PAR using some of the same methods we've just explored.

\subsection{Display options in code chunks}\label{display-options-in-code-chunks}}

The display options for code chunk headers \texttt{\{r\ ...\}} are very important to figure out in order to avoid unwanted messages in the rmarkdown document or book, and get figure headings working. Each option is separated by a comma, and follow the code chunk label. See \url{https://www.rstudio.com/wp-content/uploads/2015/02/rmarkdown-cheatsheet.pdf} for a list of these options. I've found that some of what's documented at \url{https://yihui.org/knitr/options/\#code-evaluation} doesn't work for me, so here's what I've observed: \texttt{echo=TRUE} won't display the code if \texttt{include=FALSE} is set, though the above source suggests that the \texttt{include} option only refers to chunk output.

Display options:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  no code no outputs : \texttt{include=F} {[}normal for exercises in book{]}
\item
  code no outputs : \texttt{include=T,fig.show="hide",results=F} (\texttt{include=T} is default) \texttt{results="markup"} is default (same as \texttt{TRUE}?)
\item
  code and outputs : \texttt{include=T,echo=T,fig.show=T,results=T} (return to defaults)
\item
  no code or no eval : \texttt{include=F,eval=F}
\end{enumerate}

And there are lots of other code options, like including a numbered figure caption with \texttt{fig.cap="my\ figure\ caption"}. The bookdown output extensions add citing and linking to the figure in the text, using the referencing system.

\textbf{Warnings and messages}
Turning off warnings and messages is so important in a book that I use \texttt{knitr::opts\_chunk\$set} to set these as defaults at the top of each chapter .Rmd.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}\{r echo=F\}}
\NormalTok{knitr::opts\_chunk$set(echo=T, warning=F, message=F, fig.align=\textquotesingle{}center\textquotesingle{}, out.width="75\%")}
\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}}
\end{Highlighting}
\end{Shaded}

However some things that seem like messages are actually \emph{results}, for instance:

\texttt{st\_read} will create unwanted messages that are actually results, so you can either put it in a code chunk that isn't displayed at all with \texttt{include=F} or probably better use \texttt{results\ =\ "hide"}. For instance, the following code is in a code chunk that has three options \texttt{\{r\ warning=F,\ results="hide",\ message=F\}} to avoid printing quite a lot of unwanted stuff.

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}\{r warning=F, results="hide", message=F\}}
\NormalTok{library(sf); library(igisci)}
\NormalTok{places \textless{}{-} st\_read(ex("sierra/CA\_places.shp"))}
\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}}
\end{Highlighting}
\end{Shaded}

\begin{quote}
You could of course have used that \texttt{knitr::opts\_chunk\$set} at the top of your code to avoid the warnings and messages, but you often want to see \emph{results}, so hiding them is best isolated in a code chunk that isn't producing any results you want to see, and this is typically things like \texttt{st\_read} I've found.
\end{quote}

\hypertarget{numbered-figures-with-text-citations}{%
\subsection{Numbered figures with text citations}\label{numbered-figures-with-text-citations}}

Most of the your figures are going to be created by code in an individual code chunk, and it's a good idea to create a figure heading. You should organize your code chunk so that it only produces one figure, so you can use the code chunk header to provide the figure heading, and be able to cite the figure in text just before. \emph{Note that the referencing capability requires bookdown output extensions to R Markdown, described below.}

To do this, once you've created a code chunk with an informative but unique chunk label (chunk labels cannot be reused in the document) like ``visGraph'', and also provide a figure caption with \texttt{fig.cap="..."} in the code chunk header, then in the text just above, you can use the referencing function \texttt{\textbackslash{}@ref()} to cite the figure using the \texttt{fig:} key followed by the chunk label, either including parentheses or not:

\begin{itemize}
\tightlist
\item
  \texttt{Figure\ \textbackslash{}@ref(fig:visGraph)} which produces this citation: Figure \ref{fig:visGraph}, or
\item
  \texttt{(Figure\ \textbackslash{}@ref(fig:visGraph))} which produces this citation: (Figure \ref{fig:visGraph}).
\end{itemize}

Here's what the code chunk and figure would then look like:

\begin{Shaded}

\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}\{r visGraph, fig.cap="Vegetation bar graph"\}}
\NormalTok{library(ggplot2); library(igisci)}
\NormalTok{ggplot(XSptsNDVI, aes(vegetation)) + }
\NormalTok{  geom\_bar()}
\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}}
\end{Highlighting}
\end{Shaded}

\hypertarget{building-a-book-with-bookdown-and-yaml-options}{%
\section{Building a book with bookdown and YAML options}\label{building-a-book-with-bookdown-and-yaml-options}}

While you can build a nice looking document in R Markdown, there are some other things that are useful for building a larger book out of it, like handling chapters, reference citations, and other features, so you'll want to review Xie (\protect\hyperlink{ref-Bookdown}{2021}) to learn more. We've already seen that bookdown output formats provide capabilities like figure headings and citations.

The various files for your book can be hosted as a GitHub repository (more on GitHub in the next Addendum), and published to bookdown.org to share with others. You'll want to spend some time getting it well organized for others to access, and so we will want to learn more about YAML settings to set up our book format the way we want it.

We've already looked at YAML options in the header of our .Rmd file, and for a simple report that's all we need. However, with a more complex document we might call a book, it's good practice to organize YAML settings into various places:

\begin{itemize}
\tightlist
\item
  The header to the \texttt{index.Rmd} file that starts our book off, and is typically the first chapter, which will become \texttt{index.html} following standard web practice.
\item
  \texttt{\_output.yml}: which contains the settings for each of our output formats, what in our template we just put in our \texttt{.Rmd} header.
\item
  \texttt{\_bookdown.yml}: where we put the bookdown-specific settings, like the order of our chapters.
\end{itemize}

\hypertarget{building-the-book}{%
\subsection{Building the book}\label{building-the-book}}

What we've been doing with a single .Rmd file is Knitting it to various formats, however building a book is more complex and involves more files, including chapters, bibliographic references, and other things. Here are some notes:

\begin{itemize}
\tightlist
\item
  Use the Build menu in RStudio to specify whether you want to build which type you've specified in the \texttt{\_output.yml} file. Since building a long book like this one can take a long time (about 35 minutes for both html and pdf for this book), I sometimes just build the HTML version, then build the pdf separately if it works, and since most people will use the HTML version I update that more frequently.

  \begin{itemize}
  \tightlist
  \item
    Note that pdfs don't include interactive maps except as a static rendering.
  \end{itemize}
\item
  Learn how to organize the book with chapters set aside by \texttt{\#} in markdown then subheadings at various levels using \texttt{\#\#}, \texttt{\#\#\#}, etc., and don't forget the space after the last hash.
\item
  The automatic numbering of chapters and subheadings is useful, but if you want a section to not use numbering, like this appendix, including \texttt{\{-\}} at the end of the unnumbered section header line.
\item
  Creating sections, like \textbf{Spatial}, is done by including `(PART) before the section name, like the following, which starts off the section with this special heading followed by the first chapter:
\end{itemize}

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{\# (PART) Spatial \{{-}\}}

\NormalTok{\# Spatial Data and Maps}

\NormalTok{\textasciigrave{}\textasciigrave{}\textasciigrave{}}
\end{Highlighting}
\end{Shaded}

Note that the section is excluded from the automatic numbering with \texttt{\{-\}}.

I guess I could have included some text to introduce the section but the above works to include the section name in the table of contents.

\hypertarget{special-characters-and-formatting-limitations-and-challenges}{%
\subsection{Special characters and formatting limitations and challenges}\label{special-characters-and-formatting-limitations-and-challenges}}

Handling special characters and formatting is often a challenge for automated systems that try to build graphics with nicely formatted text from an array of inputs. Code chunk headers allow another level of automation, allowing us to produce figure headings and cite them in the text. In formatting text from markdown sections, we need to turn plain text into nicely formatted text, and markdown has a lot of ways of doing this. However all of this automation runs into limitations, since we run into coding-related rules with multiple systems interacting, and this is especially true when we add LaTeX rules to things. So we need to be aware of some often surprising limitations, such as:

\begin{itemize}
\tightlist
\item
  Code chunk labels can't have underscores and other special characters like \texttt{\&} and \texttt{\_}.
\item
  Subscripts and superscripts can be confusing between html and LaTeX. See \url{https://www.math.mcgill.ca/yyang/regression/RMarkdown/example.html} .using \textasciitilde{} and \^{} like CO\textsubscript{2} and X\textsuperscript{2} might work in Rmarkdown and html, but not in LaTeX/pdf.
\end{itemize}

\section{YAML files I used to create the Introduction to Environmental Data Science book.}\label{yaml-files-i-used-to-create-the-introduction-to-environmental-data-science-book.}}

Here are some important things I've discovered in building the book. The YAML files \_output.yml, \_bookdown.yml, and the index.Rmd need to be set up right, and it's difficult to know what goes in which.

However, \emph{don't use these as a model}, unless you're going to a book publisher, and even then the settings will likely differ. But it illustrates some of the things you can do with YAML files.

\hypertarget{output.yml-for-envdatasci}{%
\subsection{\_output.yml for EnvDataSci}\label{output.yml-for-envdatasci}}

Note that there are two output sections, one the \texttt{gitbook} style of HTML which provides a table of contents panel on the left, along with the cover art, the other the \texttt{pdf\_book} section, which was the most challenging, and required working with the publisher to get the specific settings right. Building something as complex as a book often requires some tricky debugging, and since you're dealing potentially with R, Markdown, and LaTeX issues, can take a lot of effort, and if you need the format to work in a specific way (e.g.~the way a publisher might require it), I needed to learn more about LaTeX, and you can find some tricks below.

\begin{verbatim}
bookdown::gitbook:
  css: style.css
  config:
    toc:
      collapse: none
      before: |
        <li><img src="img/eaRth_anna296.png"></li>
      after: |
        <li><a href="https://github.com/rstudio/bookdown" target="blank">Published with bookdown</a></li>
    book_filename: "envdatasci"
  toc_depth: 4
bookdown::pdf_book:
  includes:
    in_header: latex/preamble.tex
    before_body: latex/before_body.tex
    after_body: latex/after_body.tex
  keep_tex: true
  dev: "cairo_pdf"
  latex_engine: xelatex
  template: null
  pandoc_args: --top-level-division=chapter
  toc_depth: 3
  toc_unnumbered: false
  toc_appendix: true
  quote_footer: ["\\VA{", "}{}"]
  highlight_bw: true
\end{verbatim}

\begin{itemize}
\tightlist
\item
  note the latex\_engine: xelatex -- that required specifying the xelatex engine, which you can set in RStudio Build/Configure Build Tools in the Sweave section of the Project Options window that will display and choosing XeLaTeX. For CRC, I needed the features this has, but didn't realize it until after a \emph{lot} of trial \& error.
\end{itemize}

\hypertarget{git-and-github}{%
\section*{Git and GitHub}\label{git-and-github}}


You'll need to learn about using Git methods to host a package on GitHub (\url{https://github.com}), where you'll also need at least a free account. See \emph{Happy Git and GitHub for the useR} \url{https://happygitwithr.com/} (Bryan (\protect\hyperlink{ref-happygitwithr}{n.d.})) to learn everything you'll need for this. Some key takeaways:

\begin{itemize}
\item
  The purpose of Git is version control, and \url{https://github.com} is a place to host package repositories (repos) that use this. Methods include keeping track of all changes in your package, including all files in the folders.
\item
  You'll need to use GitHub to create an account and connect with collaborators. And you can use it for setting everything up in your package repository.
\item
  You'll need to have the same folders on your local computer, and a method for \emph{committing} and \emph{pushing} up changes to GitHub.

  \begin{itemize}
  \tightlist
  \item
    You can use RStudio for most of this, and you'll be making all of your edits on this anyway. You'll see any changes showing up in the Git tab, where you can stage, commit, and push them to your repo.\\
  \item
    GitHub Desktop can also do commits, pushes and pulls, and is very handy for updating changes to GitHub resulting from any package editing done in RStudio (or from any other changes to files and folders in the package folder, such as external data added to \texttt{extdata}). You might also find GitHub Desktop better for dealing with moving external files and folders manually stored in the extdata folder.
  \end{itemize}
\end{itemize}

\hypertarget{some-notes-on-the-rstudio-process}{%
\section*{Some notes on the RStudio process}\label{some-notes-on-the-rstudio-process}}


See Chapter 2 in \emph{R Packages} (Wickham and Bryan (\protect\hyperlink{ref-r-pkgs}{n.d.})) for a simple process. Some observations:

\begin{itemize}
\item
  You need \texttt{devtools} and \texttt{usethis} packages.
\item
  You'll need to specify a folder with \texttt{create\_package}, and you might want to put it in a \texttt{GitHub} folder in \texttt{Documents}. It doesn't matter where, but it's useful to keep GitHub things together. Refer to Chapter 2 \url{https://r-pkgs.org/whole-game.html}.
\item
  This will create some essential files and folders:

  \begin{itemize}
  \tightlist
  \item
    \texttt{DESCRIPTION}: very important for naming and package information, which you'll be editing carefully
  \item
    \texttt{NAMESPACE}: where functions are declared, generated by \texttt{roxygen2}
  \item
    \texttt{R}: folder where your functions will go.
  \end{itemize}
\item
  Ultimately, other folders and files are created, and there's a diagram in \url{https://r-pkgs.org/package-structure-state.html} that illustrates the structure.

  \begin{itemize}
  \tightlist
  \item
    \texttt{man}: documentation on all of your functions and data sets
  \item
    \texttt{inst}: various things go in here, but I've just used it for \texttt{extdata} where you can store .csv and other files
  \item
    \texttt{data}: data (as .rda files) that can be called up like \texttt{co2} in the base R package.
  \end{itemize}
\item
  You might start by following the process in Chapter 2 for creating a simple package containing a simple function, using various \texttt{devtools} and \texttt{usethis} methods. This chapter also describes editing the \texttt{DESCRIPTION} file, using \texttt{roxygen2} to create the \texttt{man} file, how to document the function, and getting things ready to post to GitHub.
\item
  On getting things ready for GitHub, it's very useful to use \texttt{check()} from time to time to see if there are any errors in the various setup files, like \texttt{DESCRIPTION}, file \& folder structure, and documentation.
\item
  The process can be confusing, but the various RStudio methods and functions provided in \texttt{devtools} and \texttt{usethis} make it at least very easy to do if you follow directions, which are spelled out pretty clearly in the \emph{R Packages} book. We'll look at creating another function later in this appendix, following the method provided in \emph{R Packages}
\end{itemize}

\hypertarget{data-1}{%
\section*{Data}\label{data-1}}


For our package, \texttt{igisci}, we provided data in two ways:

\begin{itemize}
\tightlist
\item
  raw data as CSVs, shapefiles and TIFFs (useful since rasters don't seem to be supported in rda)
\item
  \texttt{rda} files: normal external data that are ready to use as data frames and simple feature (sf) data
\end{itemize}

\hypertarget{raw-data-in-extdata}{%
\subsection*{Raw data in extdata}\label{raw-data-in-extdata}}


Raw data (e.g.~CSVs, shapefiles, and rasters) can be simply stored in the \texttt{inst/extdata} folder. Just create those folders and put the files there. Make sure to include all the files (like the multiple files that go with a shapefile). Then, to access the data once the data package is installed, the user just needs to use the \texttt{system.file()} function to provide the path and then use that with the appropriate read function; e.g.~for a CSV, something like:

\begin{verbatim}
csvPath <- system.file("extdata","TRI/TRI_2017_CA.csv")
TRI_2017_CA <- read_csv(csvPath)
\end{verbatim}

\ldots{} or by using the \texttt{igisci::ex()} function, can be written as

\begin{verbatim}
TRI_2017_CA <- read.csv(ex("TRI/TRI_2017_CA.csv"))
\end{verbatim}

\ldots{} which isn't much different from reading data in your RStudio project folder, so seemed a useful method to include in this book. And adding data to the data package by simply putting them in the \texttt{extdata} folder is very easy and also works for data files like TIFFs that aren't supported as \texttt{rda} files that we'll look at next.

\hypertarget{binary-data-as-rda-files}{%
\subsection*{\texorpdfstring{Binary data as \texttt{rda} files}{Binary data as rda files}}\label{binary-data-as-rda-files}}


For data needed frequently, similar to \texttt{co2} or other provided data in base R, you'll want to create binary data stored as \texttt{rda} files. These files need to be prepared from data in R and go in the data folder. The process is made very easy by using \texttt{usethis::use\_data()} to add data as rda files to the \texttt{data} folder. These data can be data frames, simple features, and I'm sure other things.

I used a script \texttt{addData.R} that I put in the \texttt{inst} folder which built the data from some of the same files included in the extdata folder, with \texttt{usethis::use\_data()} to store it in the data folder. Here's a simple example with just a csv converted directly, and it takes care of storing the result in the \texttt{data} folder as an \texttt{.rda} file:

\begin{verbatim}
sierraFeb <- read_csv("inst/extdata/sierra/sierraFeb.csv")
usethis::use_data(sierraFeb)
\end{verbatim}

\hypertarget{devtoolsdocument}{%
\subsubsection*{\texorpdfstring{\texttt{devtools::document()}}{devtools::document()}}\label{devtoolsdocument}}


This creates documentation on the data sets, using the file \texttt{R/data.R}, which will need to have lines of code similar to the following to document each data set. Note that the name of the data set goes last, in quotes. The formatting of the field names and descriptions is a bit tricky and doesn't follow normal R rules. As a result, sometimes my field names don't exactly match the actual field names. Maybe I'll get around to changing the original field names with \texttt{rename}. Note that the organization is important, with the title of the data first, a blank line, then a description, etc.:

\begin{verbatim}
#' Sierra February climate data
#'
#' Selection from SierraData to only include February data
#'
#' @format A data frame with 82 entries and 7 variables selected and renamed \describe{
#'   \item{STATION_NAME}{Station name}
#'   \item{COUNTY}{County Name}
#'   \item{ELEVATION}{Elevation in meters}
#'   \item{LATITUDE}{Latitude in decimal degrees}
#'   \item{LONGITUDE}{Longitude in decimal degrees}
#'   \item{PRECIPITATION}{February Average Precipitation in mm}
#'   \item{TEMPERATURE}{Febrary Average Temperature in degrees C}
#' }
#' @source \url{https://www.ncdc.noaa.gov/}
"sierraFeb"
\end{verbatim}

Once these are on GitHub, a user can simply install the package with \texttt{devtools::install\_github("iGISc/igisci")} -- to use the \texttt{igisci} we created. Then to access the data just like built-in data, the user just needs to load that library with \texttt{library(igisci)}

\subsubsection{Removing data}\label{removing-data}}

There may be a better way, but what worked was removing the \texttt{rda} and corresponding \texttt{man} files. Also edited the \texttt{data.R} file to remove them from the \texttt{man} file maybe being created again.

We'll just look at the simple example of a function we'll name \texttt{ex()} for making it easier to read data from the \texttt{extdata} folder of the \texttt{igisci} package. The methods shown here are based on \url{https://r-pkgs.org/} which you should refer to for more thorough documentation.
